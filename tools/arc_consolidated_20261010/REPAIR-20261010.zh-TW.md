# Tokenizer 與 Notebook 輸出修復（2026-10-10）

## 已確認問題

使用者提供的 log 顯示 FULL CPU 階段完成 47,848 次檢查、可測性門檻通過；模型在 token admission 階段中止，實際生成為 0。固定 Transformers 5.8.1 的 `apply_chat_template` 預設 `return_dict=True`，但 backend 未指定此參數，回傳的 `BatchEncoding` 被既有嚴格 ID-list 契約拒絕。

接著 notebook 把完整 RESULT 印到 IOPub，造成 4 秒輸出逾時；log 記錄輸出的 notebook 膨脹至 426,612,314 bytes。此 log 開頭已截去，未收到完整 evidence archive，因此這些是原始 log 的明確觀察，不是對使用者整包 ledger 的獨立驗證。

## 修復與驗證

- 明確要求 `return_dict=False, return_tensors=None, truncation=False, padding=False`，保持原生模板、完整詞彙及嚴格 Python integer/range/token 上限驗證。沒有 flatten、轉型、截斷或 fallback。
- 終端只選取固定欄位，摘要最大 8,192 encoded bytes，不序列化大型 coverage。完整 RESULT、stage、journal、response 與封存 ZIP 不變。
- 新預設輸出為 `irisx-consolidated-20261010-repair001`；所有手動執行開關仍預設關閉。
- 287 項 Linux 測試全部通過（43.140 秒，0 失敗／錯誤／跳過）。
- 直接執行最終 notebook 完成 1,152 次 CPU SMOKE；128 控制全部符合預期，0 unknown、0 model call、0 model import。CPU 32.137 秒，總計 32.928 秒，stdout 1,661 bytes。
- 獨立逐筆核對 1,152 個 response、journal 和 archive CRC；與 v4 的 1,152 筆語義 receipt 完全一致，只排除四個量測時間欄位。
- 官方 5.8.1 方法的受控 CPU 重現得到相同舊錯誤；修正保留原 ID，接受 6,144 tokens，拒絕 6,145 與 19 種錯誤型別／數值。這使用控制的 renderer/tokenizer-call double，沒有執行完整 Granite tokenizer 或 wheel。
- compiler、inventory、demo 資料、controls、CPU budgets、dispatch、ledger、evidence、G4 硬體門檻皆維持不變。原 47,848 次 FULL 證據仍標為 v2，沒有將其改稱修復版 FULL 實跑。

1. 先保留舊 `full001` 的 log、輸出與 `archives/evidence-*.zip`（若可取得）。不要修改或刪除舊 ledger。
2. 在更新後 notebook 使用新的 kernel/session。保留新 `OUTPUT_ROOT='irisx-consolidated-20261010-repair001'` 與 `RESUME=False`；改版 source 不能接續舊帳本。
3. 要重跑完整研究，手動設 `MANUAL_START=True`、`ENABLE_MODEL=True`、`PROFILE='FULL'`。選既有 G4 RTX PRO 6000 環境、Internet Off，五個 Dataset pins 維持原版本。`MODEL_CONFIG` 與 `SESSION_SECONDS=None` 不需改動。
